# V2 local stickers

Source implementation, 2026-11-14. The native sticker panels, import/library entry points, sending, forwarded/saved markers and bounded animation renderers await the unified hosted build and real-client session.

The three sticker libraries place All, Favorites, Recent, Animated and imported packs in one horizontal category strip. Search stays within the selected category. The Animated category selects locally stored multi-frame stickers. Changing categories preserves the previous category's browsing position while the panel is open. Import can create a new pack or append to a selected existing pack. A successful import opens the destination pack. If that pack was deleted before the transaction commits, the original selection stays available for choosing another destination.

Each chat has a sticker button beside the composer. Android opens a panel below the composer, replaces the keyboard, and lets the user swipe the handle or use the expand button. The same composer button returns to the keyboard. macOS and Windows open a compact native panel above the composer without leaving the two-column chat window. The chat attachment menu opens the same panel. The main menu opens the full library for import and management.

Tap or click a tile in chat to send it with the current reply and send options. A long press on Android or the desktop context menu opens a larger in-memory preview with animation, favorite and removal actions. In the full library, clicking a tile opens its preview. The grid uses static thumbnails with an animation indicator. Import shows candidate selection, a group name and progress. Library actions use the chosen English or Simplified Chinese language. Pack names and source filenames retain their original text.

## Supported-source foundation

The read-only native catalog accepts a selected desktop folder, a single image/cache file, a standard ZIP, and the Compound File Binary Format used by classic QQ EIF. Android captures a user-granted document through its file descriptor; arbitrary access to WeChat/QQ private directories is not introduced. Android also uses the system document-tree and multiple-document selectors for user-granted images; folder traversal is bounded and file contents are validated on demand. Native desktop file/folder dialogs retain their security-scoped permissions where required.

Android accepts explicitly shared images, recognized archive types, and a single file shared as generic binary data through the system share sheet. Once MsgAT is unlocked, it detects supported formats from the granted file's bytes and opens the sticker catalog preview. The user selects candidates and confirms the destination pack before anything is saved. Sharing does not select a chat or send a sticker. If opening the share fails, the import screen can retry or reopen the system file picker. [Android receiving shared content](https://developer.android.com/develop/ui/compose/sharing/receive)

CFBF is parsed using FAT/DIFAT, directory and mini-stream structures, rather than treating EIF as ZIP. Bounds, chain cycles, offsets, sizes and directory traversal are checked. The implementation follows the [Microsoft CFB specification](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/05060311-bfce-4b12-874d-71fd4ce63aea); the classic EIF container family was identified from the original [Node QQ EIF implementation](https://github.com/momocow/Node-QQ-EIF). It is not a claim that every modern QQ export uses this format.

ZIP listing uses the central directory and matching local headers. Store and raw Deflate are supported; password protection, split/ZIP64 exports, links, unsafe names and unsupported compression return explicit errors. Entries are read into bounded RAM buffers, never extracted under their archive paths. Windows uses DeflateStream, Android uses the platform Inflater, and Mac uses the system zlib through a small native target. CRC-32 is checked before transforming an old XOR cache image.

PNG, JPEG, GIF, WebP and BMP are identified by content, including supported single-byte XOR variants of old WeChat caches. Private `wxgf`/other encrypted cache containers are not decrypted by guessing credentials or scanning another process. Unsupported items require an ordinary image/export file. Their originals are not changed or removed.

Structural dimensions and GIF/WebP frame counts are checked in the common core. Platform image codecs must additionally validate the pixels. APNG exports requiring animation should be converted to GIF/WebP; the current plan does not silently flatten their animation. Image payloads and animation bytes are retained, not transcoded into a static thumbnail as the sent asset.

## Resource bounds and ownership

Catalogs are bounded to two native sessions. Packed sources are at most 64 MiB and directory enumeration is bounded; ordinary folder images are read on demand. Catalog byte ranges and image-inspection chunks are at most 1 MiB. Native inspection holds at most two image buffers per source, clears them on completion/abort, validates CRC/format/frame bounds and calculates SHA-256 after any XOR transform. Session bytes clear when the source closes; idle sessions expire on subsequent importer access. Readers finish before their catalog is released. Android pipe-backed providers have a bounded native read timeout; ordinary filesystem operations still use the OS's IO behavior.

Initial limits: 8 MiB per image, 2048 pixels on either axis, 300 animation frames, 200 selections per confirmation, 2000 library assets and 2 GiB of library payload. ZIP/CFBF logical expansion is also bounded. All three renderers limit active animations to three, pause/release work when offscreen or inactive, and avoid an all-frame cache. Windows uses SKCodec, Mac uses ImageIO, and Android uses ImageDecoder/AnimatedImageDrawable. Animated content stays inside authenticated in-memory readers; no decrypted image URL or temporary playback file is created. Mac validates that its codec exposes all declared animation frames during import, with an explicit export-to-GIF error on unsupported platform decoding. Platform animation format/compositing behavior and resource consumption still require actual-client acceptance. [ImageIO sources](https://developer.apple.com/documentation/imageio/cgimagesource) and [WebP frame timing](https://developer.apple.com/documentation/imageio/kcgimagepropertywebpunclampeddelaytime) describe the Mac decoder APIs.

## Encrypted library foundation

`sticker_packs`, `sticker_items` and `sticker_pack_items` classify groups and assets inside SQLCipher. Content hashes deduplicate decoded image bytes; one asset can belong to several groups and/or favorites. Filenames and group names stay in the vault. Ciphertext object IDs remain random, and object keys use the unchanged root-based object importer.

All three stores scan/validate selected images, calculates the space needed for new unique assets, prepares encrypted objects and atomically commits the group, ownership and memberships. Failure/cancellation discards prepared objects through existing durable staging. Re-reading a directory-backed source is checked against the selected content hash. Removing a group's last membership releases non-favorite assets; independent favorites and other memberships survive.

`sticker_items.object_id` participates in all three clients' central object-reference views before any library cleanup can run. Deleting the last asset owner uses the existing ciphertext garbage collector. `message_stickers` and `saved_stickers` are metadata markers; the actual outgoing/saved object ownership remains in the existing message/saved-object tables. Send/save/forward operations retain these markers while creating independently encrypted owned copies, so removing a library item does not remove a sent or saved sticker. Queued forwarding fingerprints include the marker to reject changed sources. Successful sends update recent usage and consume only the captured matching reply draft in the same transaction.

The shared event schema now allows `chat.attachment.body.sticker: true` only for supported image manifests within the sticker-size limit. This preserves the same Signal envelope, upload leases, bulk transport and exact-message receipt semantics. Client coordinators insert and resolve the marker for original, received, saved and forwarded attachments. Renderers verify the encrypted object, plaintext digest, format and size before decoding; stickers render without the ordinary media card background.

## Functional surfaces and remaining acceptance

Each client exposes library groups, favorites, recents, search and paginated display, candidate thumbnails and explicit import confirmation, group rename/delete, item removal, and sending from the current conversation. Source thumbnails retain their verified content hash; import rechecks it before committing. Cancellations stop/drain source readers and library jobs before source release or vault shutdown. Android uses secure dialog flags and safe drawing insets.

Unified actual-client acceptance covers format support, GIF/WebP playback, large selections, duplicates and ownership across packs, cancel and reset, original/forwarded/saved messages, and three-client delivery. The native panels also need visual and interaction comparison for narrow windows, Android keyboard transitions, focus restoration, and immediate browsing-state changes.
