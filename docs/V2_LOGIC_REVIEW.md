# V2 业务逻辑核对

2026-11-18，业务逻辑收尾后、正式原生 UI 前，按[重构执行方案](RECONSTRUCTION_PLAN.md)核对当前源码。范围包含 Android、macOS、Windows、共享 Rust 核心和 Java 中继。本轮完成设计对照和发现项修正。编译、实机互通、断电和部署验证统一留到后续阶段。

| 链路 | 源码依据与结果 |
| --- | --- |
| 身份、密钥与本地库 | Android 检查 Keystore 的 TEE／StrongBox 安全级别，macOS 走 Secure Enclave，Windows 通过 TPM 进行实际的私钥操作。旧格式恢复同一身份时先满足硬件条件，再写硬件封装。三个客户端的资料库使用 SQLCipher，并将临时表和索引作业限制在内存。参见 `SecurePrefs`、`KeychainManager`、`TpmSecretProtector` 和各端数据库初始化。 |
| 直连中继认证 | 中继和三端都配置 TLS 1.3 并保留 TLS 1.2 兼容。普通连接用系统信任或明确的证书指纹，开发证书选项须显式开启。控制连接与附件连接分别完成认证，签名绑定客户端与服务端随机数、连接角色及 TLS 证书指纹。核对发现 Android 和 Windows 控制连接处理认证结束帧时缺少邮箱 ID 检查。现由三端共用各自的认证完成检查，要求当前挑战已处理、帧类型正确、邮箱与本次认证一致，控制和附件连接都使用该检查。见 `RelayAuthentication`、`AuthChallengeHandler` 和各端连接实现。 |
| 单聊端到端加密 | Rust 校验账号 ID 与根公钥的绑定、根签名及协议公钥。预密钥签名通过后由 libsignal 建立会话。三端仅处理匹配当前申请的预密钥目录响应，忽略已经完成或被替换的申请响应。发送事务同时保存推进后的会话状态与原密文，重试复用同一事件 ID 和密文。三端接收事务同时提交去重、业务数据、会话及预密钥状态，再确认接收。见共享 `identity.rs`、`session.rs` 及三端 `SignalProtocolStore`、`SecureMessaging`。 |
| 离线投递与回执 | 服务端在 SQLite 持久化密文后才回应已存储，并按认证收件人、发送人和事件 ID 删除确认的条目。三端用中继回执推进到灰色单勾，收到目标联系人发出的加密回执后才推进到绿色单勾或双勾。关闭已读回执时仍清理本机未读，禁止补发标记随数据库持久保存。中继配额用临时退避处理，送达恢复复用持久化密文并检查联系人状态、消息期限和原附件。见 `CiphertextMailboxStore`、`CiphertextRelay` 和三端 `SecureMessaging`。 |
| 文件与媒体传输 | 共享核心验证对象清单，以对象 ID、版本、明文大小和分块序号绑定认证加密。中继保存固定长度的密文块、完整密文摘要和下载凭据的哈希。下载时凭据经 TLS 提交给中继并与哈希匹配，内容密钥仍在端到端加密的对象清单里。上传确认在文件刷新及游标提交以后。下载续传按整块裁齐，逐块校验并在发布前核验完整密文字节及摘要。附件上传租期由当前控制连接验证，并覆盖离线邮箱的保留窗口。见 `objects.rs`、`AttachmentStore`、三端 `AttachmentTransport` 和 `AttachmentQueue`。 |
| 密文文件持久化 | Android 和 macOS 的宿主字节导入、下载终结路径在对象标记可用前同步目录。续传时发现校验通过的现成终态文件也执行该步骤。Rust 自带导入路径共用目录同步。Java 中继在 POSIX 文件系统上提交首块游标前同步暂存文件所在目录及对象根目录，最终重命名后同步目录再标记完成。Windows 继续执行分块刷新、完整校验和同目录移动。各端的断电恢复留待统一验收。 |
| 重连与首次补收 | Android、macOS 和 Windows 在首次补收连续 40 秒没有进展时关闭旧连接，沿用指数退避重连。有效的密钥发布确认或已成功处理的密文推进补收期限。只有当前同步请求匹配的完成帧才能结束首次补收。Windows 在尝试写回传输确认前处理已提交的来电及联系人状态，断线重放同一事件时仍由入站去重接管。 |
| 媒体所有权 | 三端的 `media_object_references` 覆盖消息、收藏、网页封面、头像、贴纸、缩略图、定时及原始待送达对象，并包含传输任务和传输保护记录。缩略图缓存持有加密派生对象。送达恢复只记录消息 ID 和期限，上传任务仍引用原有对象。 |
| 一对一通话 | Offer、Answer、ICE 及挑战确认经过 Signal 事件校验。收到并完成相应状态检查后，Android、macOS 和 Windows 把对端 SDP 交给 WebRTC。三端各自支持配置 TURN；聊天中继不参与通话媒体加解密。目标网络的媒体协商、直连及 TURN 回退留待统一验收。 |

## 仍需实际证明的情况

- 四个正式构建是否使用当前共享核心，三端硬件保护与 TLS 证书核验是否在目标系统和真实中继上按设计生效。
- 三端六个方向的首次会话、长期离线和预密钥换代、重连复投、回执乱序、按窗口恢复丢失的加密送达回执、关闭已读后重放，以及身份重置后的拒绝与清理。
- 文件上传和下载在数据写入、游标提交、文件发布与数据库标记之间分别中断后的恢复。覆盖磁盘不足、配额、租期不足、已下载对象损坏以及缓存清理和退后台时的行为。
- TLS 和身份认证成功后中继停止推进首次补收，以及连续收包仍有进展的慢速补收。Windows 另覆盖入站来电或联系人事件已提交、传输确认写回失败。
- 已读禁止补发、已收事件去重和预密钥使用标记共同影响重放行为。根据[已读隐私](V2_READ_PRIVACY.md)，需要保留这些标记以避免迟到密文重新生成历史回执。当前源码继续保留相关最小元数据，最终清理期限还需结合长离线和重放行为确认。

## 原生界面完成后的源码复查

- Android 搜索定位和置顶跳转引用了同一个缺失的字符串资源。默认语言和简体中文均已补齐。macOS 的附件导出偏好文件已加入 Xcode 的应用目标。
- Windows 在提交入站事务时遇到密文校验或解密错误，会回滚当前事件并继续读取后续帧。该事件不发接收确认，也不延长首次补收期限。数据库和网络写入异常仍沿用连接错误处理。Windows 收到普通公钥目录未命中时保留会话连接。
- 三端用原预密钥请求 ID 重查暂时没有公钥包的联系人。Java 中继在原请求绑定上重查，成功分配的未过期预留维持幂等。三端挑选待发送事件时会跳过仍在等公钥的联系人，有可用会话的事件仍可发送。等候中的积压不会占满其他联系人的发送候选窗口。
- 附件复查对照了三端媒体归属视图、暂存登记和提交路径。三端归属视图一致，共覆盖十种对象引用来源。通话复查对照了 Signal 通话信令、独立通话 ID、来电挑战和 WebRTC 交接。四端构建及验收产物复用流程仅做配置核对。
- 复查发现两处协议缺口。下面的源码收尾覆盖这两项。

## 统一测试前的协议收尾

- **公钥目录恢复**。中继每次启动生成新的目录代际，控制连接认证完成后通知客户端。三端在代际变化时保留账号身份与既有会话，生成新编号的预密钥并签名发布。旧代际预留不能分配一次性预密钥，仍在有效期内的旧公钥包可提供签名预密钥和 ML-KEM 最后备用密钥。旧接收密钥保留既有的 15 天以处理在途密文。
- **持续入站失败**。共享安全核心给三端同样的入站结果。暂时无法认证、解密或处理的帧延迟重试，后续帧继续处理。身份及事件 ID 均经核实的无效 V2 事件，可以与推进后的 Signal 状态一起保存确切密文的丢弃记录，只确认中继收件。记录在加密资料库内有容量上限和期限。等待原消息的编辑及撤回会在原文到达时退出等待集合，或在 15 天后清理，之前因预算不足暂缓的事件可在下一次补收时重新处理。
- 两项均已接入现有业务入口。全面测试从同一版本的 GitHub 托管四端构建开始，接着按验收矩阵进行。 [协议说明](V2_PROTOCOL.md) · [验收矩阵](RECONSTRUCTION_PLAN.md#实际使用验收与问题优先级)
